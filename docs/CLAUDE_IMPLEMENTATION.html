Claude's Implementation Notes

This file tracks, phase by phase, what was actually built against docs/DESIGN.md, plus any decisions or deviations made along the way. Each phase gets its own section, added as the phase is completed.

Phase 1 — Create models done

Built the four ActiveRecord models called for in the design: Repository, User (the "Contributor" model), PushEvent, and Request (the rate-limit tracking model from the "Rate limits" section). Generated via bin/rails generate model, then hand-edited the migrations to match the design's field-by-field spec exactly (types, uniqueness, defaults).

Schema decisions

ModelDecisionWhy
Repository github_repository_id is NOT NULL with a unique index; validated for presence + uniqueness at the model level too. Design explicitly calls for "unique constraint and index." DB-level constraint is the real guarantee; the model validation gives a friendlier error path for normal save calls.
User Same treatment for github_user_id. Design explicitly calls for "unique constraint and index," mirroring Repository.
PushEvent github_event_id is NOT NULL with a unique index (design calls this the "globally unique key from github"). repository_id / author_id are nullable foreign keys, and belongs_to is declared optional: true for both. The whole point of repository_id/author_id per the design is that they start empty and get filled in later by the enrichment fan-out (Phase 3/4) — a push event has to be a valid, savable record before enrichment ever runs.
PushEvent author association: belongs_to :author, class_name: "User", inverse_of: :push_events, backed by an author_id foreign key that references users (not the Rails-inferred authors table). Design names the column author_id but the model it points at is User; t.references :author defaults to inferring an authors table, so the migration needed an explicit foreign_key: { to_table: :users }.
PushEvent repo_unenrichable / user_unenrichable are booleans, NOT NULL DEFAULT false. These flags gate the Phase 5 backlog query (Continuous Ingestion section); they need a real default so every row is queryable from the moment it's inserted, not just after an enrichment attempt sets them explicitly.
PushEvent Added composite indexes [repository_id, repo_unenrichable] and [author_id, user_unenrichable], beyond what the design's field list strictly asks for. The design spells out the exact backlog query these support: PushEvent.where(repository_id: nil, repo_unenrichable: false) and the equivalent for authors. Since this is schema-level and the query shape is already fully specified in the design doc, it seemed better to add the supporting index now rather than as a follow-up migration in Phase 5.
Request purpose implemented as a Rails enum: { poll: 0, enrich_repo: 1, enrich_user: 2 }, NOT NULL. Matches the design's enum spec exactly.
Request poll_interval is NOT NULL DEFAULT 0. Design: "defaults to 0 seconds but uses the X-Poll-Interval response header if it was returned."
Request Index on created_at, plus a composite index on [purpose, created_at]. Design explicitly asks for the created_at index ("we'll be querying against that"). The composite index directly supports the two lookups Phase 5's IngestCycle will do every cycle: most recent Request row overall, and most recent Request row where purpose = poll.
All four models full_info stored as a plain text column, not jsonb. Design specifies "text (JSON)" — kept literal rather than upgrading to a JSON column type, since that wasn't asked for and isn't needed yet (YAGNI, per the design's own stated philosophy for these models).

Associations

  • Repository has_many :push_events
  • User has_many :push_events, foreign_key: :author_id, inverse_of: :author
  • PushEvent belongs_to :repository, optional: true
  • PushEvent belongs_to :author, class_name: "User", inverse_of: :push_events, optional: true

Testing

Wrote model tests (test/models/*_test.rb) covering, per model: presence/uniqueness validation, the underlying DB-level unique constraint (via ActiveRecord::RecordNotUnique on a raw insert! that bypasses model validation), association wiring, and the Request enum/defaults. 24 tests, 41 assertions, all green. Also ran bin/rubocop against the new migrations, models, and tests — no offenses.

Phase 2 — Pull service object (page of pushes) done

Built Github::PollPushEvents (app/services/github/poll_push_events.rb), the "Pull Service Object" from the design's poll path: it makes one GET to https://api.github.com/events?per_page=100, records a Request row describing the response, and saves a PushEvent for every entry whose type is "PushEvent". Everything else in the design's "Rate limits" and "Pull Service Object" sections that this request touches — conditional If-None-Match, per-field extraction, the logging plan, catch-and-continue on request errors — is implemented here. The budget/backlog decision of when to poll vs. enrich (Github::IngestCycle) is still Phase 5; this service object only knows how to do the poll action itself, and returns the Request it created so a future caller can use it.

Design decisions

AreaDecisionWhy
HTTP client Plain Net::HTTP, no HTTP client gem. One GET request with a couple of headers doesn't need a dependency; stdlib is enough and keeps the service object's only real collaborator visible in the code itself.
Conditional requests Before the request, look up the most recent Request row where purpose = poll and send its etag as If-None-Match, if present. Matches the design's "Rate limits" section directly: use the last etag so an unchanged feed comes back as a cheap 304.
Idempotency across polls PushEvent.find_or_create_by!(github_event_id: ...) rather than a plain create!. GitHub's public /events feed is a rolling window, so consecutive polls overlap — the same event shows up more than once. The design gives github_event_id a uniqueness constraint but doesn't say what to do about that overlap; treating a repeat as a no-op (not a WARN/ERROR) is the natural read, since it's expected steady-state behavior, not a failure.
Malformed/unparseable events A PushEvent-typed entry missing id is logged at WARN and skipped; every other field is optional on the model, so nothing else about an event can make it unsavable. Design: "if the JSON for the event cannot be parsed and we cannot add all of the fields from the PushEvent, then we will log it as WARN, and continue to the next event." github_event_id is the only field the schema actually requires.
Request-level failures A raised exception from Net::HTTP (network failure) and a 5xx HTTP response are both treated as request failures: logged at ERROR, no Request row written, method returns early with nothing saved. Design: "If a request leads to an Error being thrown, we will catch it immediately, log it as an ERROR, and move on." Also matches the later "Continuous Ingestion" note that 5xx/network failures don't get a Request row (only real responses with real headers do) — kept consistent here since it's the same rule applied to the same kind of request.
304 responses A Request row is still written (it has real headers/rate-limit info worth keeping), but the body is never parsed and no PushEvent work happens. A 304 means "nothing changed" — there's no body to speak of, but the rate-limit bookkeeping from that response is still the freshest we have.
Logging DEBUG before the fetch; INFO once the response comes back successfully; per push-event INFO ("parsed") / WARN (unparseable) followed by an INFO ("saved") once persisted; ERROR on request failure (network exception, 5xx, or unparseable JSON body). Follows the design's logging plan (a–d in "Pull Service Object") point for point.
full_info Stores event.to_json — the exact JSON object for that event as GitHub returned it, re-serialized — rather than a hand-picked subset. Design: store the full object JSON on each model so more fields can be added later without re-pulling. Applies to PushEvent the same way Phase 1 already applied it to Repository/User.

Testing

Added webmock (test group only) to stub Net::HTTP at the socket level — per the design's "we will always mock requests in tests" — and wired require "webmock/minitest" plus WebMock.disable_net_connect! into test/test_helper.rb so any un-stubbed request fails loudly instead of hitting the real GitHub API. test/services/github/poll_push_events_test.rb covers: the per_page=100 query param, saving a PushEvent per PushEvent-typed entry while ignoring other types, idempotency on a repeated github_event_id, WARN + skip on a missing id, the Request row's captured headers (etag, rate-limit remaining/reset, poll interval, status code), poll_interval defaulting to 0 when the header is absent, sending If-None-Match from the last poll's etag, a 304 short-circuiting before body parsing, and ERROR logging (with no Request row) on both a 5xx response and a raised network exception. 10 tests, 41 assertions, all green — 34 tests/82 assertions across the whole suite. bin/rubocop and bin/brakeman both clean against the new files.

Phase 3 — Pull contributors done

Before starting Phase 3, extracted the conditional-GET-plus-Request-persistence mechanics that Github::PollPushEvents (Phase 2) already had into a shared Github::ApiRequest (app/services/github/api_request.rb). Github::EnrichUser needed the exact same mechanics the design's "Continuous Ingestion" section already frames as one shared shape - "at most one HTTP request per call (poll, enrich a repository, or enrich a user)" - and Phase 4's repository enrichment is the same shape again, so extracting now rather than duplicating it a second and third time seemed like the right call. Github::ApiRequest.call(uri:, purpose:, etag:) performs the GET (with If-None-Match if an etag was given), rescues network errors, and persists the Request row - returning nil on any failure (network exception or 5xx) or a Result wrapping the raw response and the persisted Request otherwise. PollPushEvents was refactored to call it; its own Phase 2 tests were re-run unchanged afterward to confirm behavior didn't shift.

Built Github::EnrichUser (app/services/github/enrich_user.rb): given a single PushEvent that still needs its author resolved, it implements the design's "Fan Out" paragraph for contributors. It looks up whether a User already exists for that push event's github_actor_id, makes one conditional GET against GitHub's "get a user by id" endpoint (GET /user/{id}) using that user's last_etag if there is one, and then either links the push event to the (possibly just-created or just-refreshed) User, or - on a 4xx - marks the push event user_unenrichable so it permanently drops out of the backlog Phase 5 will query. Selecting which backlog push event to hand to this service is still Phase 5's job; this service only knows how to resolve one.

Design decisions

AreaDecisionWhy
Endpoint GET https://api.github.com/user/{github_actor_id} (the numeric-id form), not /users/{login}. The design deliberately stores only github_actor_id on PushEvent, not a login or URL - GitHub's REST API has a dedicated "get a user using their ID" endpoint for exactly this, so no extra field or lookup is needed.
Conditional request, always Every enrichment attempt makes one request - fresh if no local User exists yet, conditional (If-None-Match from last_etag) if one does. A known contributor is never skipped/linked for free without a request. Taken literally from the design's Fan Out wording: "If we haven't, we will pull the information. If we have, we'll use the etag... to do a conditional request" - both branches make a request, they just differ in whether it's conditional. This also matches Phase 5's one-cycle-one-request model.
Deduplicating contributors Looked up by github_user_id and updated in place (find_by + assign_attributes/save!), never a second row for the same id - a repeat 304 or 200 for an already-known contributor still just links the existing row. Design: "we're going to see if we have already saved that information in the database" before deciding how to request it - the whole point is one User row per contributor no matter how many of their push events get enriched over time.
4xx handling Sets user_unenrichable = true on the push event and does not touch the User table; the Request row is still persisted (it's a real response, not a failure to get one). Design: "If the request was meant to enrich a user or repository and the response was a 4xx error, then set the corresponding... field... and do not attempt again."
5xx / network failure handling No Request row, push event untouched (still eligible for the backlog next cycle), ERROR logged. Same "Error thrown... catch immediately, log ERROR, move on" rule Phase 2 already applied to the poll request - a transient failure isn't the same as a permanent 4xx, so it shouldn't set user_unenrichable.
Missing github_actor_id Immediately marks the push event user_unenrichable, logs WARN, makes no HTTP call at all. Not explicitly in the design, but a necessary edge case: without an id there's no endpoint to call, and leaving it enrichable would mean this row sits in the Phase 5 backlog query forever, wasting a cycle every time it's picked. This is the same purpose the _unenrichable flags already serve for real 4xx responses.
Guard clauses call is a no-op (no HTTP call) if the push event already has an author_id or is already user_unenrichable. Phase 5's backlog query already filters these out before this service is ever invoked, but making the service itself idempotent/safe to call directly keeps it independently testable and correct if invoked outside that query.

Testing

test/services/github/enrich_user_test.rb covers: creating a new User and linking it on a fresh 200, sending no If-None-Match when nothing is known yet, sending it (and linking without creating a duplicate) when a User is already known and GitHub returns 304, updating an existing User's fields in place when a 200 comes back with changed data, two push events by the same author converging on one User row, marking user_unenrichable (with the Request still persisted) on a 4xx, ERROR logging with no Request row and no state change on a network failure, the blank-github_actor_id guard (WARN, zero HTTP calls), and the two already-enriched/already-unenrichable no-op guards. 11 tests, 42 assertions, all green - 45 tests/124 assertions across the whole suite. bin/rubocop and bin/brakeman both clean.

Phase 4 — Pull repositories done

Built Github::EnrichRepository (app/services/github/enrich_repository.rb) - the repository half of "Fan Out", and structurally a direct mirror of Phase 3's Github::EnrichUser: given a single PushEvent that still needs its repository resolved, it looks up any existing Repository by github_repository_id, makes one conditional GET against GitHub's "get a repository by id" endpoint via the shared Github::ApiRequest, and either links the (created or refreshed) Repository or, on a 4xx, marks the push event repo_unenrichable so it permanently drops out of the Phase 5 backlog query. No new shared code was needed - Github::ApiRequest already covered the request/response mechanics.

Design decisions

AreaDecisionWhy
Endpoint GET https://api.github.com/repositories/{github_repository_id} (the numeric-id form), not /repos/{owner}/{repo}. Mirrors the reasoning for users in Phase 3: the design stores only github_repository_id on PushEvent, and GitHub's REST API has a dedicated "get a repository using its ID" endpoint for exactly that, so no owner/name lookup is needed.
Everything else Same shape as Github::EnrichUser: always one request (fresh or conditional depending on whether a local Repository already exists), dedup by github_repository_id with in-place updates rather than new rows, 4xx → permanent repo_unenrichable with the Request still persisted, 5xx/network failure → ERROR logged, no Request row, push event left retryable, blank github_repository_id → immediate repo_unenrichable with no HTTP call, guarded no-op if already enriched/unenrichable. The design's Fan Out and Rate-limit sections describe contributors and repositories with parallel language throughout ("for each contributor and repository..."), so there was no reason for the two enrichment paths to diverge in behavior - only in which model and endpoint they touch.

Testing

test/services/github/enrich_repository_test.rb mirrors enrich_user_test.rb's eleven cases one-for-one against Repository/repo_unenrichable/repository_id instead of User/user_unenrichable/author_id. 11 tests, 42 assertions, all green.

Environment fix: disabled test parallelization. Adding this phase's 11 tests pushed the suite from 45 to 56 tests, crossing Rails' default parallel-test threshold (50) for the first time. That activated parallelize(workers: :number_of_processors) in test_helper.rb - 12 workers on this machine, each needing its own cloned test database - and that cloning step hung indefinitely in this environment (confirmed by forcing PARALLEL_WORKERS=1, which ran all 56 tests in 0.17s). Since this suite runs in well under a second single-process and Phase 8's Docker Compose test service will invoke bin/rails test the same way, leaving parallelization on would hand the reviewer the identical hang the moment the suite crossed 50 tests - which it now permanently has. Changed test_helper.rb to parallelize(workers: 1) rather than rely on an env var override reviewers wouldn't know to set.

Phase 5 — Github::IngestCycle budget/backlog logic done

Built Github::IngestCycle (app/services/github/ingest_cycle.rb), the decision algorithm from the design's "Continuous Ingestion" section, implemented point-for-point against the numbered list there. It composes the three service objects from Phases 2-4 (PollPushEvents, EnrichRepository, EnrichUser) but makes none of the underlying HTTP calls itself - it only decides which of those three to call, or whether to call none of them this cycle. As the design specifies, it has no knowledge of jobs, queues, retries, or sleeping; it returns a small Result (decision, request, ratelimit_reset) and leaves scheduling entirely to whatever calls it - the rake task and Solid Queue job that Phases 6 and 7 will build.

Design decisions

AreaDecisionWhy
Decision order Cold start (no Request row at all) → poll. Else rate-limit floor check → else poll-interval check → else backlog check → else idle. Follows the design's numbered list in "Deciding what to do this cycle" exactly, including its explicit cold-start override ("assume full budget and poll immediately").
Rate-limit floor RATE_LIMIT_SAFETY_FLOOR = 5, checked against the most recent Request row of any purpose. Design: "the most recent Request row (any purpose)... the ground truth from Github's last response to us, whichever entry point made it" and "a safety floor (e.g. 5)."
Backlog query A single query: PushEvent.where(repo_unenrichable: false, repository_id: nil).or(PushEvent.where(user_unenrichable: false, author_id: nil)).order(:created_at).first - the union of both needs-repo and needs-user, oldest first. Matches the design's backlog definition and "enrich the oldest backlog item" verbatim - one query rather than two separate lookups, since "oldest across either queue" is what the design asks for.
A backlog item needing both repo and user enrichment Repository enrichment is tried first (push_event.repository_id.nil? && !push_event.repo_unenrichable? is checked before falling through to user enrichment). Since only one HTTP request happens per cycle, this item will need to come up again on a later cycle for the other half. The design doesn't state an order for this case explicitly. Repo-before-user was picked arbitrarily but applied consistently - "at most one HTTP request per call" already means one side has to wait either way, and the item stays in the backlog (still author_id: nil) so it's picked up again rather than lost.
Errored requests within a cycle IngestCycle doesn't distinguish a decision that failed from one that succeeded - Github::PollPushEvents/EnrichUser/EnrichRepository already log the ERROR and return nil internally (Phases 2-4); IngestCycle just passes that nil through as Result#request. Design: "the cycle logs the error; the caller reschedules with the same computed wait as any other cycle rather than a special backoff, since the next cycle will simply attempt the same work again" - no special handling needed here because the underlying service objects already log and the next cycle's state (unchanged Request/backlog) naturally causes a retry.
Result shape Struct.new(:decision, :request, :ratelimit_reset, keyword_init: true), with decision one of :poll, :enrich_repository, :enrich_user, :rate_limited, :idle. Phases 6/7 need to know what to reschedule for. ratelimit_reset is only populated for :rate_limited, since that's the only branch where the design says the caller needs it ("the caller reschedules for ratelimit_reset"); the other branches' wait computation (a fixed idle wait, or "the same computed wait as any other cycle") doesn't need anything else from this service.
EnrichUser/EnrichRepository return value Both now end their call method by returning result.request (the Request row Github::ApiRequest persisted), matching PollPushEvents' existing contract. Small tweak made before writing IngestCycle, so it can compose all three service objects the same way without an extra query to re-find the request each one made. Existing Phase 3/4 tests assert database state, not return values, so this didn't require touching them.

Testing

test/services/github/ingest_cycle_test.rb covers: cold start (zero Request rows) polling immediately, the rate-limit floor short-circuiting with zero HTTP calls, polling once the poll interval has elapsed, falling through to enrichment when it hasn't, prioritizing repository enrichment over user enrichment for an item needing both (asserting the user endpoint is never requested that cycle), picking the globally oldest backlog item ahead of a newer one, idling when nothing is due, and excluding a push event that's _unenrichable on both sides from ever reappearing in the backlog. 8 tests, 22 assertions, all green - 64 tests/188 assertions across the whole suite. bin/rubocop and bin/brakeman both clean.

Phase 6 — Rake task ("repeatable") done

Built lib/tasks/ingest.rake, defining ingest:once - the "repeatable" entry point from the design's "Continuous Ingestion" section. It's intentionally thin: depend on :environment, call Github::IngestCycle.call exactly once, log the decision, and let Rake exit normally. All of the actual behavior (what to do, rate limiting, backlog priority) already lives in Github::IngestCycle (Phase 5) and the service objects underneath it - this task has nothing to decide. This is also the task Phase 8's ingest Docker Compose service will run via bin/rails ingest:once.

Design decisions

AreaDecisionWhy
Task body Three lines: call Github::IngestCycle.call, log "[ingest:once] cycle complete, decision=#{result.decision}", done. No loop, no sleep, no rescue wrapper. Design: "a rake task (ingest) calls Github::IngestCycle directly and synchronously, once, then exits." Looping/rescheduling is explicitly the continuous job's job (Phase 7), not this task's.
No top-level rescue An unexpected exception (e.g. a real bug, DB unreachable) is allowed to propagate and exit the task non-zero. Every failure mode the design actually anticipates (network errors, GitHub 4xx/5xx, unparseable JSON) is already caught and logged several layers down, inside PollPushEvents/EnrichUser/EnrichRepository/ApiRequest (Phases 2-5). A truly unexpected exception reaching this task means something outside those anticipated cases broke, and a one-shot task run via docker compose run --rm ingest should surface that as a visible failure rather than exit 0 silently.
STDOUT logging in development No change needed. The design's "Docker / Rails wiring this requires" section flags config/environments/development.rb as needing a STDOUT logger fix so docker compose logs -f shows this task's output. Checked it while building this phase: this Rails 8.1 app's generated development.rb already sets config.logger = ActiveSupport::TaggedLogging.logger(STDOUT) (line 80) out of the box - that concern predates this scaffold's Rails version and doesn't apply here.

Testing

test/tasks/ingest_task_test.rb loads the app's Rake tasks once at file load and re-enables ingest:once before each test (Rake tasks otherwise only run once per process). Covers: invoking Github::IngestCycle exactly once on a cold start (asserted via a Request row appearing), the decision being logged, and an idle cycle making zero HTTP calls. 3 tests, 5 assertions, all green - 67 tests/193 assertions across the whole suite. bin/rubocop and bin/brakeman both clean.

Also ran bin/rails ingest:once for real against the live (unauthenticated) GitHub API and the local dev database - not just the mocked test suite - to confirm the whole chain actually works end to end: it polled https://api.github.com/events, persisted a Request with the real ETag/rate-limit headers GitHub returned, saved 97 real PushEvent rows, and logged [ingest:once] cycle complete, decision=poll. Reset the dev database back to empty afterward.

Phase 7 — Solid Queue job ("continuous") done

Built GithubIngestJob (app/jobs/github_ingest_job.rb), the "continuous" entry point from the design's "Continuous Ingestion" section: perform calls Github::IngestCycle.call once and self-reschedules with self.class.set(wait: ...).perform_later, so the chain keeps going unattended as long as bin/jobs is running. Also wired up the config/recurring.yml heartbeat entry the design calls for, and along the way found and fixed a pre-existing bug that left Solid Queue completely unable to run outside production.

Found and fixed: Solid Queue was broken in development and test. config/environments/development.rb sets config.solid_queue.connects_to = { database: { writing: :queue } }, but config/database.yml only ever defined the primary/cache/queue/cable multi-database split for production - development and test each had just a single flat database: key, with no queue role at all. Confirmed this was a real, live bug before writing any Phase 7 code: SolidQueue::Job.count raised ActiveRecord::AdapterNotSpecified ("The queue database is not configured for the development environment") in development, and PG::UndefinedTable: relation "solid_queue_jobs" does not exist in test (where, absent any connects_to override, it silently fell back to the primary connection instead). Since GithubIngestJob and its chain_alive? heartbeat check both depend on querying SolidQueue::Job, this was a hard blocker for Phase 7, not a pre-existing tech-debt item to leave alone.

Fixed by adding a queue role to database.yml for both development (strongmind_development_queue) and test (strongmind_test_queue) - separate physical databases on the same Postgres server, mirroring production's structure exactly rather than collapsing roles together - and adding the matching config.solid_queue.connects_to line to config/environments/test.rb (only development/production had it before). Ran db:prepare for both environments afterward to create and schema-load the two new databases, and confirmed SolidQueue::Job.count now works in both. Did not touch the equivalent likely gap for solid_cache/solid_cable (development also sets config.cache_store = :solid_cache_store with no matching cache role) - that's unrelated to this phase's job and out of scope unless asked.

Design decisions

AreaDecisionWhy
Job body perform is two lines: call Github::IngestCycle.call, then self.class.set(wait: self.class.wait_for(result)).perform_later. No loop inside perform - each execution is one cycle, matching IngestCycle's own "at most one HTTP request per call, then returns" contract. Design: "calls Github::IngestCycle, then computes a wait... and re-enqueues itself." The design's own prose says perform_later(wait: ...), but that option only exists on .set(...) in ActiveJob - self.class.set(wait: ...).perform_later is the actual API for a delayed self-enqueue.
Wait computation (wait_for) Public class method, not a private instance helper: :rate_limited → time remaining until ratelimit_reset, floored at 1 second; :idle → a flat IDLE_WAIT (30 seconds); everything else (:poll, :enrich_repository, :enrich_user) → a flat BASE_WAIT (1 second). Matches the design's three distinct cases verbatim: "the caller reschedules for ratelimit_reset," "a short idle wait," and "the same computed wait as any other cycle" for everything else (poll, enrich, or a request that errored - IngestCycle doesn't distinguish those at the decision level, see Phase 5). Made it a public class method specifically so it's unit-testable against constructed Results without needing to drive a full cycle through WebMock for every wait-timing case.
No top-level rescue in perform Same reasoning as Phase 6's rake task: an unexpected exception is allowed to fail the job rather than being swallowed. This is exactly the scenario config/recurring.yml's heartbeat exists for - design: "if the self-rescheduling chain ever dies from an unhandled error, this re-enqueues GithubIngestJob so ingestion doesn't stay silently stalled." Catching everything here would defeat that safety net's purpose.
Heartbeat idempotency (chain_alive? / ensure_running) recurring.yml calls GithubIngestJob.ensure_running, not perform_later directly. ensure_running only enqueues a fresh job if chain_alive? is false, where chain_alive? is SolidQueue::Job.where(class_name: "GithubIngestJob", finished_at: nil).exists?. Design: the heartbeat "is not the primary driver of pacing" and only matters "if the self-rescheduling chain ever dies." An hourly entry that unconditionally called perform_later would instead start a brand new parallel self-perpetuating chain every single hour on top of any already-healthy one, since nothing would ever stop the old chain - SolidQueue::Job's own finished_at IS NULL state (covers queued, scheduled, and in-flight) is what lets the heartbeat tell "already running" apart from "actually died" without adding any new tracking of its own.
recurring.yml environment scoping Restructured with a shared default: &default anchor (mirroring config/queue.yml's existing pattern in this same repo) applied to both development and production, rather than adding the new entry only under the pre-existing production: key. The file previously had a production: section only, meaning the pre-existing clear_solid_queue_finished_jobs entry - and a heartbeat added the same way - would never fire under docker compose up, which runs RAILS_ENV=development (per Phase 1's own notes). Same class of environment-scoping gap as the queue_adapter/STDOUT-logger items the design already flagged elsewhere; worth fixing now since this is the first phase that gives recurring.yml an entry that actually matters.

Known local-environment issue: bin/jobs itself segfaults on this machine. Running the actual bin/jobs Solid Queue supervisor (which forks separate dispatcher/worker processes) crashed with a segmentation fault inside the pg gem's native C extension (connect_start), triggered while a freshly-forked child process tried to open its own Postgres connection. This reproduced consistently and is a known general class of issue with the pg gem/libpq and fork() (particularly around OpenSSL state) - not a bug in GithubIngestJob, Github::IngestCycle, or any other Phase 1-7 code: the identical logic ran correctly, twice in a row, with no fork involved (perform_now above), and the full mocked test suite (which also never forks) is green. This is almost certainly specific to this machine's Ruby/pg/macOS build (a very recent Ruby patch revision) and not expected to reproduce inside the Linux container Phase 8 will run bin/jobs in - but it's worth being aware of if bin/jobs needs to run directly on this host again outside Docker.

Phase 8 — Docker Compose wiring done

Added the three services the design's "Docker Compose Wiring" section calls for — jobs, ingest, test — plus one not in the design's original list: migrate, added mid-phase once live testing surfaced a real startup race (see below). All four reuse the same Dockerfile.dev build and DATABASE_*/env shape web already had. Verified against a real Docker daemon on this machine, not just by reading the compose file: built and brought the full stack up from a completely clean volume state (docker compose down -v first) multiple times, ran the live GitHub-ingestion chain for real through jobs, and ran both docker compose run --rm test and docker compose run --rm ingest.

Design decisions

AreaDecisionWhy
jobs Runs bin/jobs, same build/env as web, not profiled — starts automatically under docker compose up --build. Design: "Not profiled - it starts automatically under docker compose up --build, alongside db and web, since continuous ingestion is meant to run unattended as part of 'the system.'"
ingest / test Both given profiles: ["tools"]; each still runs its own bin/rails db:prepare defensively before its real command. Design, verbatim: "profiles: ["tools"] so docker compose up --build doesn't try to start it... docker compose run --rm ingest still works, since run targets a named service explicitly regardless of its profile" and "re-run db:prepare defensively... in case a reviewer runs [it] without having brought docker compose up up first."
test database RAILS_ENV: test, same db container/host, no second Postgres service. Design: "Rails keeps dev and test as separate databases on the same Postgres server via database.yml, so no second database service is needed" — confirmed true here since database.yml's test: block already points at its own strongmind_test/strongmind_test_queue databases (Phase 1/7).
Bundle install on every service command Every service's command is prefixed with bundle check || bundle install && before the real command, rather than relying solely on the image's build-time RUN bundle install. Found via live testing, not in the design: web's named bundle_cache volume is mounted at /usr/local/bundle, which shadows whatever the image's build step installed the moment the volume already existed from an earlier build (e.g. a stale volume from before webmock was added to the Gemfile in Phase 2). Confirmed this concretely: docker compose up --build against the pre-existing local bundle_cache volume failed both web and jobs with Bundler::GemNotFound for webmock and friends, even though the image had just rebuilt with a Gemfile that includes it. This is the same tradeoff the volume was presumably added for in the first place (avoid a full bundle install on every container start) — bundle check keeps that fast path on the common case and only reinstalls when the volume's gem set actually drifts from the Gemfile.lock.
New migrate service One-shot service running only bin/rails db:prepare, depended on by web and jobs via condition: service_completed_successfully (in addition to db: condition: service_healthy). Found via live testing, not in the design: with both web and jobs independently running their own bin/rails db:prepare on container start (needed so either one works if brought up alone), a completely fresh Postgres volume let both processes race to run CREATE DATABASE/schema-load concurrently. Reproduced this directly — a from-scratch docker compose up --build against a freshly-created, empty postgres_data volume failed web with PG::ConnectionBad: FATAL: database "strongmind_development" does not exist while jobs' own concurrent db:prepare was mid-flight. Pulling the one-time "create and migrate everything" step out into its own service that both web and jobs block on is the standard Compose pattern for exactly this - it removes the race entirely rather than papering over it with a retry/sleep. ingest and test don't depend on migrate: they're invoked one at a time via docker compose run --rm, never concurrently with each other or with a fresh web/jobs startup in the reviewer's actual workflow, so they keep their own standalone-safe db:prepare instead.
Bootstrapping the continuous chain on first boot jobs' command runs bin/rails runner 'GithubIngestJob.ensure_running' immediately before bin/jobs. Found via live testing, not in the design: config/recurring.yml's github_ingest_heartbeat entry (Phase 7) only fires "every hour" - on a fresh docker compose up with zero SolidQueue::Job rows, nothing ever calls GithubIngestJob.perform_later the first time, so the chain would sit completely idle for up to an hour before its first cycle. Confirmed this directly: querying SolidQueue::Job.where(class_name: "GithubIngestJob").count right after a clean docker compose up --build (before this fix) returned 0. Design: "if the self-rescheduling chain ever dies from an unhandled error, this re-enqueues" - the heartbeat's own stated job is restarting a dead chain, not starting the first one, so seeding it here doesn't change the heartbeat's role, it just closes the gap of who does the first perform_later. Reused ensure_running (already idempotent/no-op-if-alive from Phase 7) rather than an unconditional perform_later, so re-running docker compose up against an already-running chain doesn't start a second parallel one.

Verification

All done against a real Docker daemon on this machine (started fresh for this phase), not just by reading the compose file:

  • docker compose up --build -d from a completely clean state (docker compose down -v beforehand, removing both the Postgres data volume and the bundle cache volume) — confirmed only db, migrate, web, jobs start (never ingest/test), migrate exits 0 before web/jobs come up, web serves on :3000, and jobs' Solid Queue supervisor registers its Dispatcher/Worker/Scheduler processes and loads both recurring tasks.
  • Let the continuous chain run for real against the live, unauthenticated GitHub API through several dozen cycles (SolidQueue::Job.where(class_name: "GithubIngestJob").count climbed well past 40) — watched it actually poll, then fall through to enriching real repositories and users, matching Github::IngestCycle's decision order.
  • docker compose run --rm test — 78 runs, 214 assertions, 0 failures, matching the host-run suite exactly.
  • docker compose run --rm ingest — ran one real cycle against the live API and logged [ingest:once] cycle complete, decision=..., sharing the same db container/state as the already-running jobs chain.
  • While both jobs and a manually-run ingest were hitting the live backlog concurrently, observed one real Github::EnrichUser race (two processes enriching the same push event's author at once) surface exactly the caught-and-logged path already built in Phase 3: User#save! raised on the DB's unique constraint, save_user's rescue StandardError logged it as an ERROR and returned the (nil, in this case) existing_user, and the push event's author_id was left nil - so it just gets retried next cycle rather than corrupting anything. Left as-is rather than "fixed": this is the same class of accepted, self-healing race the design's own "Known gap" section already names for the Request table, just showing up in a second place under real concurrent load - not a Phase 8 scope item.
  • Reset local state afterward with docker compose down -v so the repo is left exactly as a reviewer's clean checkout would find it - no leftover containers, volumes, or local Postgres data from this session's testing.
